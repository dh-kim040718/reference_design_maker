# Phase 6 — 로컬 출시 준비

**최신 진행:** [금액 통제·운영·배포 준비](./phase-6-operations.md)에 전역 예산 예약/차단, 원장 복원 보강, 운영자 점검·출시 검사, 컨테이너 빌드·로컬 실행 검증을 기록했다. 사용자 결정에 따라 원본 비보관·자동 재개 제외, 배포/백업 대상 미정으로 로컬 준비까지만 수행한다. 아래 과거의 ‘금액 통제/작업 큐 후속’ 설명보다 이 최신 결정을 우선한다.

**백업·복원 선행 구현:** [앱 데이터 백업·복원 기록](./phase-6-backup-recovery.md)에 로컬 스냅샷·격리 DB 복원·삭제 결과 재등장 방지·AI 작업 미재생 규칙과 실제 PostgreSQL 훈련 결과를 기록했다. 운영 백업/보존 기간·전체 장애 복구 게이트는 아직 미완료다.

실제 제공자/운영 환경 확인은 [보류 작업 체크리스트 API-17~20](./deferred-api-work.md)에서 추적한다. 키 없이 진행 가능한 작업 큐·백업·모니터링 등은 이 문서와 개발계획에서 별도로 관리한다.

2026-11-02: API 키 없이 실행 가능한 검사와 운영 절차를 선행했다. 원격 CI 실행·배포·운영 백업·실사용자 출시는 수행하지 않았으며 Phase 6 완료를 의미하지 않는다.

## 반복 가능한 무료 검사

저장소 루트에서:

```powershell
npm.cmd test --prefix frontend
npm.cmd run build --prefix frontend
npm.cmd run lint --prefix frontend
node scripts/check_public_artifacts.mjs
npm.cmd test --prefix browser-extension
backend/.venv/Scripts/python.exe scripts/package_collector.py --check
```

공개 산출물 검사는 프런트엔드 빌드와 확장 소스의 텍스트 파일에서 OpenAI 키·Supabase 비밀 키·개인키·민감 환경 변수의 리터럴 할당을 검사한다. `.env`를 읽거나 일치한 값을 출력하지 않는다. CI의 프런트엔드 빌드 직후에도 실행한다. 알려진 패턴 검사이며 난독화·분할된 값·모든 비밀 형식을 탐지한다는 보장은 없다. 바이너리·ZIP은 이 검사의 범위가 아니며 확장 ZIP은 별도 패키지 일치 검사로 소스와 비교한다.

브라우저 회귀 검사는 API 서버와 프런트엔드를 실행한 뒤 frontend에서 실행한다. 프런트엔드 프록시 대상 포트가 현재 API 서버와 일치해야 한다. 예: API 서버가 8000이면 개발 프로세스에만 `$env:VITE_API_PROXY_TARGET='http://127.0.0.1:8000'`을 설정한다.

```powershell
node browser-smoke.mjs chrome --thumbnail --generation
node browser-smoke.mjs edge --thumbnail --generation
```

생성 비활성화 상태에서 저장·메모 수정·재조회·생성 차단·로컬 마스크 PNG·390px 가로 넘침·로그아웃을 확인한다. 실제 생성 버튼은 누르지 않는다.

## 데이터·장애 대응

- 생성 원본은 서버에 영구 저장하지 않는다. 메모 스냅샷·추가 요청·상태와 비공개 생성 결과는 DB에 남는다. 삭제 시 결과 본문을 지우고 중복 과금 방지·횟수 기록은 유지한다.
- 현재 프로젝트/유형의 보관은 삭제가 아니다. 계정 영구 삭제·백업 보존 기간·복구 목표·복원 자동화는 아직 확정/구현되지 않았다. 운영 환경을 선택한 뒤 정책을 확정하고 격리된 환경에서 복원 훈련을 통과해야 한다.
- 외부 생성 장애 시 `IMAGE_GENERATION_ENABLED=false`를 유지/적용하고 API 프로세스를 재시작한다. 저장 MVP는 계속 제공한다. 불명 요청은 자동 재전송하거나 중복 방지 기록을 삭제하지 않는다.
- 키 유출/회전 시 제공자에서 기존 키를 폐기하고 서버 환경의 새 키를 설정한 뒤 프로세스를 재시작한다. 키를 명령 인자·채팅·보고서에 넣지 않는다. 설정 파싱 실패 메시지도 원본 출력 전에 비밀 포함 여부를 확인한다.
- 금액 기반 차단은 아직 구현되지 않았다. 일 3회 제한을 금액 상한으로 안내하지 않는다. 운영 활성화 전 제공자 측 예산 설정과 앱의 금액 기반 통제, 분산 작업/재시작 정책을 별도로 검증한다.
- 현 상태는 작업별 상태·처리 시간·제공자 토큰 사용량 조회를 제공한다. 운영용 집계 대시보드·알림·작업 큐는 후속 작업이다. 오류 관찰 시 원본 이미지·토큰·메모·제공자 원시 응답을 수집하지 않는다.

## 출시 전 남은 게이트

1. Phase 4 실제 생성 성공·품질·청구 검증. Phase 5 영역 편집은 기준 미달/미검증 시 출시 대상에서 제외한다.
2. 모바일 실기기 공유와 지원 환경 검증, HTTPS 운영 환경에서의 회귀 검사.
3. 운영용 작업 큐·금액 통제·보존/백업 정책과 복원 검증·관측/알림 구성.
4. 배포 대상과 비밀 주입 방식 확정, 원격 CI 통과, 제한된 사용자 출시 및 저장 완료율/오류율 관찰.

실행한 검사와 실제 배포/운영 검증을 구분해 관리한다. 최신 로컬 브라우저 결과는 아래 실행 기록에 추가한다.

## 오류 진단·작업 안정성 보강 — 2026-11-02

### 안전한 제공자 진단

- 작업에 `provider_http_status`와 고정된 `provider_reason`만 저장한다. 원시 메시지·헤더·API 키·프롬프트는 보관하지 않는다. Alembic head는 `0007_safe_diagnostics`이며 로컬 앱 DB에 적용했다.
- 진단 분류는 인증, 권한, 모델/경로 사용 가능 여부, 잔액/할당량, 요청 제한, 잘못된 입력, 콘텐츠 정책, 제공자 장애, 시간 초과, 연결 실패다. 상태 코드만으로 상세 원인을 확정하지 않으며 화면에서는 확인할 항목을 안내한다.
- 오류 본문은 최대 16KiB까지만 해석하고 알려진 코드만 분류에 반영한다. 예상하지 못한 코드/분류는 버린다. `insufficient_quota`일 때만 429를 잔액/할당량으로 구분한다. 그 외 429는 요청 제한으로 안내한다.
- HTTP 5xx·네트워크/시간 초과는 과금 결과가 불명확할 수 있어 `unknown`으로 남긴다. 자동 재시도하지 않는다. 4xx는 `failed`로 기록하지만 무과금을 보장하지 않는다.
- 기존 실패 기록의 HTTP 상태·상세 원인은 복원할 수 없다. 다음에 별도 승인된 실제 검증을 할 때부터 새 진단이 적용된다.
- 분류의 기반: [OpenAI 공식 오류 코드 문서](https://developers.openai.com/api/docs/guides/error-codes). 새 분류는 실제 API 호출 없이 `httpx.MockTransport`로 검증했다.

### 오래된 작업 정리와 늦은 응답 차단

- 앱 시작 시 및 30초마다 DB에서 5분 넘게 갱신되지 않은 `queued`/`processing`을 `unknown`으로 전환한다. 서버를 재시작해도 원본/마스크를 재전송하지 않는다. 최근 작업은 유효 기간까지 유지하므로 다른 프로세스의 정상 작업을 시작 즉시 중단하지 않는다.
- 새 요청 예약에서도 해당 사용자의 오래된 작업을 먼저 정리한다. 이력을 방문하지 않아도 오래된 작업이 새 요청을 영구 차단하지 않는다. 기존 한도 사용량은 반환하지 않는다.
- 오래된 대기 작업은 실행 직전에도 확인해 제공자 호출 없이 종료한다. 원자적 상태 변경으로 동일 작업을 중복 실행하지 않는다.
- 제공자 호출 뒤에는 아직 `processing`이고 삭제되지 않은 작업만 완료 상태로 바꾼다. 정리된 작업에 늦은 결과가 돌아와도 `unknown`을 덮어쓰거나 삭제한 이미지를 되살리지 않는다. 보류된 결과는 자동 재활용/재요청하지 않는다.
- 제공자 호출 중 DB 읽기 트랜잭션을 유지하지 않는다. DB 오류 발생 시 작업 매개변수를 포함할 수 있는 원시 예외를 로그로 출력하지 않고 고정 메시지만 남긴다. 주기 정리의 DB 장애는 고정 경고 후 다음 주기에 다시 확인하며 제공자는 호출하지 않는다.
- 이는 상태 복구 보강이다. 원본을 영구 저장하는 작업 큐·성공 결과의 재시작 복원·금액 기반 차단·운영 집계/알림은 아직 구현하지 않았다. 실제 요청 완료 여부/청구는 별도 확인이 필요하다.

## 계정별 AI 사용 현황 — 2026-11-02

- 생성 입력/결과 화면의 **내 AI 사용 현황 보기**에서 최근 7일 또는 30일 기록을 조회한다. 펼칠 때와 기간 변경/새로고침 때만 조회하고 자동 폴링하지 않는다. 이 동작은 생성/편집 API를 호출하지 않는다.
- `GET /api/v1/generation-metrics?days=7` 또는 `days=30`은 인증된 본인 계정의 기록만 반환한다. 다른 기간 값은 422이며 응답은 `Cache-Control: no-store`다. 전 계정 집계나 관리자용 공개 엔드포인트를 만들지 않았다.
- 기간은 현재 UTC 날짜를 포함한 7/30개 날짜의 시작 자정부터 조회 시각까지다. 작업 예약 시각(`created_at`)을 기준으로 하며 삭제한 결과와 실패/불명 요청도 포함한다. 집계 전 본인 계정의 오래된 작업을 정리한다.
- 전체/생성/편집 건수, 상태별 건수, 종료 상태 기준 성공 비율, 안전한 실패 사유별 건수, 측정된 종료 작업의 평균·95백분위 처리 시간과 표본 수, 제공된 총 토큰 합계와 사용량 제공/누락 건수를 반환한다.
- 성공 비율 분모는 `succeeded + failed + unknown`이다. 대기/진행 작업은 분모와 사용량 누락 집계에서 제외한다. 지연 표본은 성공·실패·불명 중 유효한 측정값이 있는 작업이다. p95는 정렬된 측정값의 nearest-rank 값이다.
- 사용량 0이 명시된 경우만 0으로 집계하며 누락·잘못된 JSON·음수·불리언·허용 범위 초과 값은 미제공으로 처리한다. 데이터가 없으면 성공 비율/처리 시간은 null이다. 실제 청구액은 항상 미확정(null)으로 둔다. 요청 기록 수가 실제 과금 횟수라는 의미는 아니다.
- DB 조회는 필요한 상태·작업 종류·시간·사용량·안전한 오류 분류 컬럼만 선택한다. 이미지·메모·프롬프트·키·URL·작업 ID·레퍼런스 ID는 응답에 포함하지 않는다. 알려지지 않은 오류 분류는 `unspecified`로 합쳐 원문을 노출하지 않는다.
- DB 스키마 변경은 없어 Alembic head `0007_safe_diagnostics`를 유지한다. 백엔드 전체 129개(SQLite/PostgreSQL)·프런트엔드 47개, 빌드·양쪽 lint·공개 산출물 비밀 검사를 통과했다. 이번 화면은 컴포넌트 mock으로 검증했으며 추가 실브라우저/운영 배포 검증은 하지 않았다.
- 이 단계는 계정별 관측의 최소 구현이다. 전 계정 운영자 대시보드·알림·장기 지표 저장·인프라 지표·실제 청구 연동은 아직 없다. 실제 호출/운영 확인은 [API 보류 체크리스트](./deferred-api-work.md)의 미완료 상태를 유지한다.
