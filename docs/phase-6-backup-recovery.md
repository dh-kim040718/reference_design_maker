# Phase 6 — 앱 데이터 백업·복원 준비

2026-11-02: 로컬 PostgreSQL 앱 데이터의 수동 백업과 격리 복원 도구를 구현하고 실제 복원 훈련을 수행했다. 운영 백업 구축이나 전체 Supabase 장애 복구 완료를 의미하지 않는다. 유료 AI 호출은 없다.

## 구현 범위

- 프로젝트·산출물 유형·레퍼런스·사용자 마지막 경로·생성/편집 작업·일별 호출 예약을 한 트랜잭션에서 읽어 UTF-8 JSON 스냅샷으로 저장한다. PostgreSQL에서는 repeatable-read/read-only 트랜잭션을 사용한다.
- 현재 앱 스키마는 `0009_project_concepts`다. 알려진 이전 0007/0008 백업은 손상 확인 후 메모리에서 호환 변환하고 과거 금액은 미확정, 과거 시안은 단일 참고 scope로 유지한다. 업그레이드 전의 알려진 스키마도 반영된 실제 컬럼으로 백업할 수 있다. 포맷·알려진 스키마·테이블/컬럼 집합·SHA-256이 맞지 않으면 복원을 중단한다. 해시는 우발적 손상 확인용이며 전자서명이나 암호화는 아니다. 신뢰할 수 있는 로컬 백업만 입력한다.
- 새 파일만 생성하며 기존 백업을 덮어쓰지 않는다. CLI는 로컬 PostgreSQL만 지원하고, 매번 새 `rdm_restore_...` DB를 만든다. 기존 DB 이름 재사용·비어 있지 않은 복원 대상·일반 앱 DB 대상은 거절한다. DB 삭제나 실제 앱의 연결 대상 변경은 수행하지 않는다.
- 현재 모델로 대상 스키마를 생성하고 백업의 버전을 기록한다. 복원 후 모든 행/컬럼을 다시 읽어 예상 내용과 비교한다. 검증 실패 시 데이터 입력 트랜잭션은 롤백하고 격리 대상은 운영에 사용하지 않는다. 생성된 빈 스키마/DB가 남을 수 있으며 자동 삭제하지 않는다.
- 백업 파일은 `.phase6-backups/<UTC 시각>_<식별자>/app-snapshot.json`, 내용 없는 요약은 `report.json`이다. 디렉터리를 Git 제외 처리했다. CLI는 키·연결 비밀번호·사용자 콘텐츠를 출력하지 않는다.

## 포함·제외와 개인정보

백업에는 앱 메모·링크·썸네일·비공개 생성 결과가 포함될 수 있으므로 민감한 사용자 데이터로 취급한다. 현재 로컬 파일은 암호화되지 않는다. Git 제외는 암호화나 접근 통제가 아니므로 공개 폴더·배포 산출물·일반 CI 아티팩트에 넣지 않는다.

`.env`, OpenAI 키, Supabase Auth 계정/세션/비밀번호, 업로드 전 원본·마스크 메모리는 포함하지 않는다. Supabase의 Auth·Storage·플랫폼 설정을 통째로 백업하는 도구가 아니다. 계정 복구 시 원래 사용자 ID와 앱 소유권을 유지해야 하며 Auth/Storage 복구는 운영 환경에서 별도 검증해야 한다.

백업 보관 기간·주기·원격 보관 위치·암호화 키 관리·자동 삭제는 아직 정하지 않았다. 사용자 데이터 백업을 임의 주기로 삭제하는 작업도 추가하지 않았다. 운영 전 제안은 일 1회 백업·최근 7일 보관·RPO 24시간·RTO 1시간이지만, 이는 미합의 목표이며 달성한 보장이 아니다. 실제 데이터 규모·플랫폼·비용에 맞춰 확정해야 한다.

## 삭제·AI 작업 복원 규칙

1. 복원 직전에 현재 원본 DB의 삭제된 생성 작업 ID와 현재 썸네일 해시를 읽는다. 원본에 접속할 수 없으면 CLI 복원은 진행하지 않는다.
2. 백업 이후 삭제된 생성 결과도 복원 시 이미지 본문을 지우고 삭제 상태를 유지한다. 삭제한 결과가 오래된 백업에서 되살아나는 문제를 방지한다.
3. 백업 이후 제거/변경된 썸네일은 과거 이미지로 되돌리지 않고 비운다. 프로젝트/유형의 보관은 삭제와 구분하며 상태를 복원한다.
4. `queued`/`processing`은 `unknown`으로 복원하고 결과 본문을 비운다. 원본·마스크를 저장하거나 작업을 자동 재생하지 않는다.
5. 요청 ID·입력 해시·일별 예약 횟수·삭제 이력은 유지한다. 복원 때문에 과금 방지 기록을 초기화하거나 사용 횟수를 환급하지 않는다.
6. 금액 원장도 포함한다. 백업 후 새로운 유료 예약 기록이 있으면 과거 스냅샷 복원을 거절하고 새 스냅샷을 요구한다. 현재 원본의 금액 예약보다 낮은 값으로 복원하지 않는다.

이 규칙은 **원본이 살아 있는 로컬 복원 훈련**에 적용한다. 삭제 조회 이후의 동시 변경까지 막는 운영 복원 절차는 아니다. 실제 전환 전에는 쓰기 중단과 최신 삭제 기록 재확인이 필요하다. 원본 전체 장애 시에도 삭제를 존중하려면 별도 내구성 삭제 원장과 보존 정책이 필요하며 아직 구현하지 않았다. 계정 영구 삭제·참조 데이터의 영구 삭제 정책도 후속 범위다.

## 실행 방법

저장소 루트에서 아래처럼 backend로 이동해 실행한다. 스냅샷 생성/복원은 앱 키와 무관하며 AI 제공자를 호출하지 않는다. DB 연결 설정은 서버 `.env`에서 메모리로만 읽고 명령 인자로 전달하지 않는다.

```powershell
Push-Location backend
# 새 백업만 생성
.venv/Scripts/python.exe -m app.backup snapshot

# 새 백업 → 별도 신규 DB → 행 내용 검증
.venv/Scripts/python.exe -m app.backup drill

# 기존 백업을 새 격리 DB로 복원 (현재 원본의 삭제 상태를 반드시 반영)
.venv/Scripts/python.exe -m app.backup restore --snapshot ../.phase6-backups/<실행폴더>/app-snapshot.json
Pop-Location
```

복원 DB에는 API 서버를 자동 연결하지 않는다. 정리할 때도 원본과 복원 DB를 먼저 구분하고, 백업/보고서를 보존할지 결정한 뒤 정확한 대상만 별도 승인 범위에서 정리한다. 도구에는 자동 drop 기능이 없다.

- 2026-11-02 `.phase6-backups/20261102_020503_e563673e/report.json`에서 격리 복원 `verified=true`, 제공자 호출 0회를 확인했다.
- 프로젝트 25개·유형 25개·레퍼런스 29개·사용자 경로 3개·생성 작업 6개·일별 예약 1개가 모두 내용 비교를 통과했다. 원본 DB는 읽기만 수행했다.

- SQLite 자동 테스트로 전체 내용·생성 결과·예약 횟수 복원, 백업 후 삭제/썸네일 제거 반영, 진행 작업 결과 불명 전환, 파일 변조·덮어쓰기·기존 대상·앱 DB 대상 거절을 확인했다. PostgreSQL은 실제 CLI drill로 검증했다.
- 백엔드 회귀 140개 통과·4개 제외, lint·공개 산출물 비밀 패턴 검사 통과. 제외된 4개는 공통 테스트 fixture의 PostgreSQL 백업 케이스이며, 격리되지 않은 기존 트랜잭션에서 스냅샷을 만드는 대신 위 실제 PostgreSQL CLI 훈련으로 별도 검증했다. 자동 테스트로 PostgreSQL의 백업 후 삭제 시나리오까지 확인했다는 의미는 아니다. Starlette/httpx 경고 1개는 남아 있다.
- 운영 스케줄·원격 암호화 백업·원본 장애 시 삭제 원장·Auth/Storage 복원·RPO/RTO 달성·정기 복원 훈련은 아직 미완료다.
