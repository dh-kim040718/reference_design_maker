# 실제 API 연동 보류 작업 — 재개 체크리스트

**생성 단위 정정:** 아래 실제 성공/비용 기록은 과거 단일 참고 및 편집 실험이다. 2026-11-02부터 신규 UX는 [프로젝트 전체 종합 생성](./project-ai-concepts.md)이며 기존 API-06 완료를 새 다중 입력 검증으로 간주하지 않는다.

- [ ] **PROJECT-01 실제 다중 이미지 연동:** 별도 예산/정확한 호출 수 승인과 과거 청구 대조 후 프로젝트 전체 이미지·번호별 메모가 실제 제공자에 전달되는지 확인한다.
- [ ] **PROJECT-02 종합 유용성/충돌 처리:** 서로 다른 분류의 레이아웃·차트·색감 메모를 종합하고 요구사항을 우선하는지 평가한다. 메모 없는 자료·상충 메모도 대표 사례로 기록하며 기존 결과를 재사용한다.
- [ ] **PROJECT-03 실제 프로젝트 입력 비용:** 다중 이미지 토큰·시간·청구액과 예약 단위를 대조한다. 과거 한 장의 USD 0.012534 추정을 프로젝트 전체 단가로 간주하지 않는다.
- [ ] **PROJECT-04 실결과 재방문/재생성:** 실제 종합 결과의 프로젝트 스냅샷·이력·다운로드·삭제·현재 입력으로 재생성 준비를 검증한다. mock 성공과 실결과를 구분한다.
- [ ] **PROJECT-05 큰 프로젝트 후속 설계:** 16개/합계 16MiB/32,000자를 넘는 경우의 분할 검토/요약을 별도 설계·평가한다. 현재는 명시적으로 차단하며 일부를 자동 생략하지 않는다.

**최신 재개 결과:** [Phase 4·5 실제 평가](./phase-45-live-evaluation.md)를 먼저 확인한다. 승인된 재생성 1회·편집 2회를 수행했다. API-12의 마스크 검증은 수행 완료이지만 보호 영역 보존은 실패했고, API-16은 출시 제외·비활성화 결정 완료를 뜻한다. 실제 청구 확인과 사용자 수용 항목은 미완료다.

최종 정리: 2026-11-02. 사용자 요청으로 API 키·실제 제공자 접근·유료 호출이 필요한 작업을 뒤로 미뤘다. 아래 항목을 완료 증거 없이 완료 처리하지 않는다. 키 설정 자체는 사용자가 이미 수행했으며, 남은 문제를 단순히 “키 없음”으로 기록하지 않는다.

## 현재까지 확인한 사실

- 최초 실행 시도는 연결 오류로 `unknown`이었다. 사용자는 이후 Usage 화면에서 선택한 프로젝트의 요청 0회·USD 0을 확인했다.
- 사용자 승인으로 총 USD 1 예산 내 1회 재시도했으나 `PROVIDER_REJECTED`로 실패했다. 그 당시 HTTP 상태/상세 원인은 보관되지 않아 복원할 수 없다. 재시도 이후 실제 청구액은 아직 확인되지 않았다.
- 같은 키로 모델 조회 HTTP 200은 확인했지만 이미지 생성 권한이나 생성 성공을 확인한 것은 아니다.
- 키 노출 이후 사용자가 `.env`의 키를 교체했다고 알렸다. 키 값은 이 문서나 실행 기록에 기록하지 않는다.
- 생성·편집 성공, 실제 결과 품질·시간·장당 비용은 미검증이다. 실제 편집 제공자 어댑터도 아직 없다.
- **후속 갱신:** 2026-11-02 10:36 KST 새 키로 별도 승인한 1회 실행에서 전체 생성이 처음 성공했다. 11,130ms·1,066토큰과 기본 시각 확인·동일 요청 기존 작업 반환을 기록했다. 실제 청구액·사용자 유용성 평가·실제 편집은 여전히 미검증이다. 아래 API-06 완료 증거를 참고한다. 앞선 실패 원인은 새 키 성공만으로 확정하지 않는다.
- HTTP 상태·안전한 오류 분류, 중복 요청 방지, 횟수 제한, 오래된 작업 정리, 편집 입력 계약과 mock 테스트는 구현돼 있다. 이 구현을 실제 연동 성공으로 간주하지 않는다.

## 재개 원칙

- 현재 기본값은 생성/편집 비활성화다. 이 체크리스트 작성이나 이후 일반 개발 요청을 유료 호출 승인으로 해석하지 않는다.
- 기존 USD 1·건별 1회 승인은 이미 시도에 사용됐다. 다음 실행 전 실제 사용 내역과 잔여 예산을 확인하고 추가 호출 수를 명시적으로 승인받는다. USD 1은 제공자 지출을 강제로 차단하는 설정이 아니다.
- mock과 기존 결과를 우선 재사용한다. 실제 호출은 mock으로 대체할 수 없는 최종 연동·품질·비용 확인에만 사용하고 자동 재시도하지 않는다.
- `.phase4-checks/live-attempt.json`과 `.phase4-checks/approved-retry-02/live-attempt.json`을 삭제/덮어써서 재실행하지 않는다. 새로 승인된 시도는 별도 폴더에 입력·계획·영구 호출 기록·결과·보고서를 남긴다.
- 실제 실행은 네트워크 접근이 허용된 환경에서만 한다. 권한/연결 문제를 유료 요청 재전송으로 진단하지 않는다. 키·로그인 정보·원본 오류 본문을 명령 인자나 로그에 노출하지 않는다.

- [ ] **API-02 계정/모델 준비 확인:** 현재 서버 키의 유효성, 대상 프로젝트, 모델 사용 가능 여부, 이미지 생성 권한, 필요한 조직 인증/결제 상태를 확인한다. 키 원문은 남기지 않는다.
- [x] **API-03 계약/단가 재확인:** 고정 모델·이미지 편집 엔드포인트·JSON 입력·출력 크기/품질·최신 공식 단가를 다시 확인한다. 모델을 임의 교체하지 않는다. 변경 필요 시 구현/mock 계약을 먼저 수정·검증한다.

## Phase 5 — 전체 재생성·실제 영역 편집

- [x] **API-12 제공자 마스크 계약 실검증:** 같은 크기의 PNG 마스크에서 투명 영역만 편집되는지, 입력 포맷/용량·출력 크기가 유효한지 확인한다. 로컬 좌표/alpha 테스트와 서버 검증 통과만으로 제공자 준수를 확정하지 않는다.
- [x] **API-13 지시 유무 비교:** 같은 입력·마스크·기존 방향으로 명시적 지시가 있는 편집과 지시 없는 변형을 비교한다. 기존 결과가 유효하면 재사용하고 필요한 호출 수만 승인받는다.
- [x] **API-14 실제 편집 전체 흐름:** 요청→처리 상태→결과→이력→다운로드·삭제, 기존 방향/선택 지시 표시, 추가 유료 요청 없는 동일 ID 재조회, 전체 생성과 공유하는 한도 적용을 확인한다.

- [x] **API-16 Phase 5 출시 판정:** 기준을 통과한 경우에만 실제 영역 편집을 활성화한다. 미달/미검증이면 비활성화하고 로컬 마스크 도구만 유지한다. 사각형 이외 브러시/다중 영역은 이번 필수 보류 범위가 아니다.

## Phase 6 — 실제 제공자/운영 환경에서만 끝낼 수 있는 확인

- [ ] **API-17 금액 통제 실효성:** 금액 기반 통제를 구현한 후 제공자 예산/사용 내역과 맞춰 한도 도달·실패/불명 과금 대응을 확인한다. 현재 UTC 일 3회 제한은 금액 상한이 아니다. 설계·mock은 키 없이 선행 가능하다.
- [ ] **API-18 운영 비밀 주입/회전:** 배포 환경을 정한 뒤 서버 전용 키 주입·키 누락·회전/폐기·접근 권한을 확인한다. 로컬 키 교체와 운영 검증을 구분한다. 절차 작성/mock은 선행 가능하다.
- [ ] **API-19 배포 환경의 실제 연동:** HTTPS 운영 환경에서 저장 MVP와 실제 생성/편집 흐름을 확인한다. 장애·지연·결과 불명 시 성공으로 표시하지 않는지, 생성 비활성화 시 저장이 유지되는지 확인한다. 필요 호출은 건별 승인한다.
- [ ] **API-20 제한된 사용자 평가:** 합의한 출시 범위에서 시안 유용성·실패율·시간·비용을 관찰하고 활성화/제한 여부를 결정한다. 로컬 mock 통과나 한 장 성공을 운영 품질 보장으로 해석하지 않는다.

## 재개 순서와 기록 방법

`API-01~04 준비 → API-05~09 생성 검증 → API-10~16 재생성/편집 검증 → API-17~20 운영 확인` 순서로 진행한다. 실제 편집 어댑터의 문서 검토·mock 구현처럼 호출 없는 작업은 선행할 수 있다.

각 항목 완료 시 체크 표시와 함께 **확인 날짜, 코드/테스트 또는 보고서 경로, 실측 결과, 비용 확인 출처, 미해결 제한**을 바로 아래에 남긴다. 하나의 결과로 여러 항목을 검증했으면 같은 보고서를 참조한다. 이전 실패 기록은 그대로 보존한다. Phase 4/5/6 완료 표시는 각 게이트를 별도로 확인한 뒤 바꾼다.
