# Phase 6 — 금액 통제·운영·배포 준비

2026-11-02 사용자 결정: **원본 비보관 정책 유지·자동 재개 제외**, **배포/백업 대상 미정이므로 로컬 준비까지만 수행**한다. 외부 배포나 사용자 데이터 전송, 자동 예약 작업 설치, 유료 AI 호출은 수행하지 않았다.

## 금액 기반 요청 통제

- `GENERATION_BUDGET_USD`는 모든 계정·생성/편집을 합친 누적 예약 한도다. 기본값 0이며 미설정 시 새 유료 예약을 차단한다. UTC 자정에도 금액 예약은 초기화되지 않는다.
- `GENERATION_RESERVATION_USD`는 요청당 미리 확보할 예산이다. 기본값 USD 1, 소수 6자리까지 허용한다. 실제 장당 가격·공식 최대 청구액을 뜻하지 않는다. 1 USD는 1,000,000 micro-USD 정수로 기록한다.
- DB의 단일 전역 예산 행을 잠근 뒤 남은 금액을 검사·예약한다. 일별 횟수 제한·계정별 진행 1개 제한도 유지한다. PostgreSQL 두 연결이 마지막 1 USD를 동시에 요청해도 하나만 수락됨을 검증했다.
- 같은 요청 ID 재제출은 기존 작업을 반환하므로 예약액을 추가 차감하지 않는다. 입력·작업 종류가 바뀌면 충돌로 거절한다. 금액 초과는 429, 예산 미설정/과거 청구 대조 필요는 503이다.
- 성공 토큰 사용량을 실제 청구액으로 간주해 예약을 자동 반환하지 않는다. 실패·결과 불명·삭제·재시작도 예약을 해제하지 않는다. 미처리 과거 요청 또는 예약 원장의 불일치가 있으면 새 예약을 차단한다.
- `GET /generation-policy`의 `budget`은 예산 예약 상태이며 실제 청구액은 null이다. 화면에 미설정·예산 소진·기록 확인 필요를 구분해 표시한다.
- 원장은 `generation_budget`, 작업별 예약액은 `generations.reserved_micro_usd`에 보관한다. `0008_budget_reservations`를 로컬 앱 DB와 테스트 DB에 적용했다. 과거 6개 작업은 실제 청구가 확인되지 않아 예약액 null로 남기며 임의로 0원 처리하지 않았다.

이 기능은 **앱이 추가 요청을 접수하는 금액 기준**이다. 제공자 측 실청구 차단이나 결제 연동이 아니며 예약 단위가 실제 청구를 과소평가하면 금액 상한을 보장할 수 없다. 실제 활성화 전 공식 단가/입력 상한, 충분한 예약 단위, 제공자 측 예산 설정, 기존 Usage/Billing과 원장 대조가 필요하다. 기존 총 USD 1 테스트 승인을 운영 예산으로 자동 적용하지 않았고 `.env`도 바꾸지 않았다.

실제 청구 대조와 운영자 수정 감사 절차는 아직 확정하지 않았다. 확인 없는 과거 비용 입력·예약 반환·수동 SQL 원장 초기화를 하지 않는다. 활성화는 해당 절차를 마련하고 대조한 뒤 진행한다.

## 작업 재시작 정책 — 사용자 확정

원본/마스크는 메모리에서만 처리하고 영구 큐용 페이로드를 저장하지 않는다. 따라서 서버 재시작 후 자동 재개는 이번 출시 범위에서 제외한다. 기존 원자적 실행 선점·중복 방지, 시작/30초 주기의 오래된 작업 정리, 늦은 응답 덮어쓰기 방지를 사용한다. 정리된 작업은 `unknown`이며 과금/예약을 자동 환급하거나 제공자를 재호출하지 않는다. 기본 단일 API worker를 유지한다.

## 백업 연계 보강

- 스냅샷은 금액 원장과 작업별 예약도 포함한다. 현재 원본의 예약 잔액보다 낮은 잔액으로 복원하지 않는다.
- 백업 이후 새로운 생성/편집 요청 ID가 존재하면 오래된 스냅샷 복원을 거절한다. 과금/중복 방지 기록을 잃지 않도록 새 스냅샷을 요구한다.
- 이전 `0007_safe_diagnostics` 백업은 원본 파일을 바꾸지 않고 메모리에서 0008 형식으로 올린다. 과거 요청 예약액은 null로 두어 청구 확인 전 새 요청을 차단한다. 손상 검사 후 알려진 스키마만 변환한다.
- 새 0008 스키마로 실제 로컬 PostgreSQL 복원 훈련을 통과했다. 보고서는 `.phase6-backups/20261102_021659_acbf1629/report.json`이다.
- 원본 전체 장애 때 삭제 기록/예약 원장을 대조할 별도 내구성 원장, 원격 암호화 백업, Auth/Storage 복원과 보관 기간은 운영 대상 결정 후 진행한다. 자세한 범위는 [백업 기록](./phase-6-backup-recovery.md)을 따른다.

## 운영자 점검과 알림

backend에서 실행한다.

```powershell
.venv/Scripts/python.exe -m app.operations
.venv/Scripts/python.exe -m app.release_check
```

`operations`는 공개 HTTP API가 아닌 로컬 운영자 CLI다. 전 계정 상태별 건수·오래된 작업 수·금액 예약 상태와 고정된 알림 코드만 JSON으로 출력한다. 이미지·메모·프롬프트·키·사용자/작업 ID를 포함하지 않는다. DB 상태를 읽기만 하며 제공자를 호출하지 않는다.

종료 코드: 0=현재 알림 없음, 2=확인 필요한 상태, 1=DB 접근 실패. 확인 항목은 오래된 작업·결과 불명·과거 청구 미대조·활성 기능의 예산 차단이다. 원시 DB 오류는 출력하지 않는다. 이번 로컬 실행에서는 결과 불명 1건·이전 요청 6건의 청구 대조 필요를 감지했다. 스케줄러/대시보드/외부 알림 전송은 설치하지 않았다. 향후 대상에서 5분 주기 실행과 종료 코드 관찰을 설정할 수 있지만 운영 주기는 미확정이다.

`release_check`는 HTTPS Auth·정확한 HTTPS CORS origin·DB·활성 기능의 키/예산·편집 품질 제한을 검사한다. 설정 통과만으로 배포를 승인하지 않고 실제 청구/수용·원격 백업·Auth/Storage 복구·모바일 실기기·원격 CI·HTTPS 회귀·알림 스케줄러를 수동 게이트로 남긴다. 현재 로컬 HTTP 설정이 차단되는 것은 정상이며 검사를 통과시키려고 `.env`를 바꾸지 않았다.

## 컨테이너 배포 준비

`backend/Dockerfile`, `frontend/Dockerfile`, `frontend/nginx.conf`, 루트 `compose.yaml`을 추가했다. API는 일반 사용자 권한·단일 worker로 실행하고 DB 준비 상태 `/health/ready`를 healthcheck로 확인한다. Nginx는 SPA fallback과 `/api/`, `/health/` 프록시를 제공하며 원본+마스크 업로드를 위해 본문 한도를 24MiB로 설정했다.

Compose는 별도 배포용 환경 파일 `APP_ENV_FILE`을 반드시 요구한다. 로컬 `.env`를 암묵적으로 배포하지 않는다. 기본 공개 포트도 `127.0.0.1:8080`뿐이며 외부 HTTPS/TLS 설정은 포함하지 않는다. 컨테이너에서 DB/Auth의 localhost는 호스트 PC를 가리키지 않으므로 실제 도달 가능한 전용 주소를 설정해야 한다.

실제 배포 전 순서: 배포/백업 대상 확정 → 별도 비밀 주입 방식 마련 → 원격 DB 백업/격리 복원 → 마이그레이션 → release check와 수동 게이트 확인 → 이미지 빌드/고정 → HTTPS 설치·회귀 → 제한 출시. DB 마이그레이션은 컨테이너 시작 때 자동 실행하지 않는다. 기반 이미지 태그와 백엔드 의존성은 아직 완전한 digest/lock 고정이 아니므로 운영 릴리스에서는 빌드 식별자와 의존성을 고정해야 한다.

구성/빌드 검증에는 공개 예시 파일만 사용했다.

```powershell
$env:APP_ENV_FILE='.env.example'
docker compose --env-file .env.example config --quiet
docker compose --env-file .env.example build
```

위 명령은 운영 실행 명령이 아니다. 예시의 SQLite/로컬 Auth 설정으로 운영 서비스를 띄우지 않는다. `.dockerignore`로 키 파일·가상 환경·로컬 백업이 빌드 컨텍스트에 포함되지 않도록 했다.

`app.container_smoke`는 별도 복원 DB·API 키 없는 임시 env 파일·임시 컨테이너/네트워크를 사용해 루프백에서만 SPA/프록시/DB 준비를 확인한다. 실제 로컬 검증은 통과했으며 `.phase6-backups/container_smoke_c6eb8cd7a9/report.json`에 기록했다. 임시 리소스와 DB 연결용 env 파일은 종료 시 정리한다. 공개 배포·Auth 전체 흐름·모바일 실기기 검증을 대신하지 않는다.

CI에 두 컨테이너 이미지 빌드 작업을 추가했다. 원격 CI는 실행하지 않았으며 기존 frontend/backend/PostgreSQL 작업과 함께 향후 푸시 시 검증할 준비만 했다. 이미지 레지스트리 push나 외부 메시지 전송은 없다.

## 이후 실제 환경에서 남은 항목

사용자가 배포/백업 대상을 미정으로 정했으므로 다음 항목은 실제 대상 확정 후 수행한다.

1. 실제 청구액과 생성 시안 수용, 과거 사용 대조·원장 수정 감사 절차, 운영 예산/예약 단위 결정.
2. 암호화·원격 백업 위치·보존 기간·삭제 원장·Auth/Storage 복구, RPO/RTO 및 복원 훈련.
3. 운영 알림 실행 주기·수신 방식, HTTPS/비밀 주입·키 회전·원격 CI와 배포 후 회귀.
4. 모바일 실기기 설치/공유와 지원 환경 확인, 제한 사용자 출시.

영역 편집은 품질 미달로 계속 제외하며 자동 재개 큐는 사용자 결정으로 제외했다. 출시 완료로 표시하지 않는다.

## 이번 실행 검증 기록

- 백엔드 160개 통과·6개 제외. 제외된 항목은 공통 fixture의 PostgreSQL 백업 시나리오이며 실제 PostgreSQL CLI 복원 훈련을 별도 수행했다. 자동 테스트의 제외 항목까지 PostgreSQL에서 모두 검증했다는 뜻은 아니다. Starlette/httpx 호환성 경고 1개는 남아 있다.
- 프런트엔드 48개와 타입 검사 포함 빌드·lint, 백엔드 lint·공개 산출물 비밀 검사 통과.
- PostgreSQL 독립 연결 2개의 마지막 1 USD 경합에서 하나만 수락됨을 확인했다. 테스트 전용 무작위 스키마만 생성·정리했다.
- Compose 구성 확인과 API/Web 이미지 빌드 통과. 별도 복원 DB·API 키 없는 임시 컨테이너에서 SPA/프록시/DB 준비 상태를 확인했다. 임시 컨테이너·네트워크가 남아 있지 않고 연결용 임시 env 파일도 삭제된 것을 확인했다. 빌드 이미지는 로컬 Docker에 남아 있다.
- 실제 운영자 CLI는 결과 불명 1건과 이전 비용 미대조 6건을 알림으로 반환했고, 출시 검사도 로컬 HTTP와 수동 운영 게이트를 정상적으로 차단했다. ‘출시 검사 통과’로 기록하지 않는다.
- 실제 API 호출 0회, `.env` 수정 없음, 외부 배포/원격 백업/알림 설치/원격 CI 실행 없음. 로컬 준비 범위를 넘는 작업은 수행하지 않았다.
